A

核心判断

维度 论文 代码
回答什么 为什么这样设计、否掉了哪些方案 现在到底怎么跑
时效 滞后，常落后代码一年以上 实时
覆盖 核心思想 配置、异常、性能细节
成本 一篇 1 到 2 小时 一个模块 1 到 3 天
一句话

前 2 到 3 篇论文收益极高，之后陡降。把时间留给代码和真实负载。

B

为什么不能只读代码

代码只剩结果，没有取舍过程。比如 block 为什么是 16 个 token、为什么 V1 不再分 prefill 和 decode 阶段、为什么抢占选择重算而不是换出。

论文还给出评估框架：指标怎么定义、baseline 怎么选、实验怎么设计。这些决定了你能不能判断一个新方案是否值得上生产。

C

为什么不能论文优先

vLLM 的 SOSP 论文写的是 V0：BlockManager、swap、copy-on-write。现在的 V1 是 token 预算调度、多进程、异步调度。照论文去找对应类会找不到。

论文数量还在爆炸，大部分是增量工作。读完再读代码，时间成本过高。

D

三个阶段

  1. 第 1 周地基读 docs/design，读 PagedAttention 论文，跟一条请求走完
  2. 第 2 周主线调度器与 KV cache，跑真实负载并 profile
  3. 第 3-4 周分支选一个方向深挖：kernel、投机解码、分离式、编译
  4. 持续问题驱动用 issue 和 PR 反推设计意图

第一阶段完成后，你应该能画出请求从 HTTP 到 GPU 的完整链路。notes/vllm-architecture.html 就是这条线。

E

先读什么：一条主线

只跟一条链，不要散读。这条链走通，vLLM 的骨架就通了。

对应的阅读顺序：

  1. vllm/entrypoints/llm.py：LLM 类怎么发起请求。
  2. vllm/v1/engine/llm_engine.py：add_request 与 step 的循环。
  3. vllm/v1/engine/core.py：EngineCore.step 是全文的心脏。
  4. vllm/v1/core/sched/scheduler.py：schedule 与 update_from_output。
  5. vllm/v1/core/kv_cache_manager.py：allocate_slots 与 block 生命周期。
  6. vllm/v1/executor/abstract.py：执行器接口，再看 multiproc_executor.py。
  7. vllm/v1/worker/gpu_worker.py：Worker 初始化四件事。
  8. vllm/v1/worker/gpu_model_runner.py：只读 _update_states、_prepare_inputs、execute_model。
  9. vllm/model_executor/models/registry.py，再挑一个模型读透。

K

读代码的方法

按调用链读，不要按目录读。从 LLM.generate 或 POST /v1/chat/completions 出发，一路跟到 kernel。

每读一个模块，回答三个问题：

  1. 输入和输出是什么。
  2. 状态存在哪里，谁持有。
  3. 失败时谁负责清理。

测试是另一种规格说明。先看 tests/ 里的用例，再读实现，能快速确认边界条件。

L

什么时候回去读论文

  • 代码里的常量或结构看起来随意，比如 block size、batch 上限、阈值。
  • 想改策略，但不知道还有哪些备选方案。
  • 方案评审或面试要讲清 tradeoff。

带着问题读，一篇 1 到 2 小时。读完马上回到代码验证。

M

掌握程度的判断

满足这四条，就算掌握了主线：

标准 具体表现
讲得清 不看代码，能口述一步请求经过哪些函数
改得动 能预测改 max_num_batched_tokens 对吞吐和延迟的影响
定位得到 出现 TTFT 抖动或吞吐下降，能定位到具体模块
说得明 能解释 V1 为什么放弃 V0 的 prefill 与 decode 分阶段
N

常见误区

误区 后果 改法
从第一个 commit 开始读 陷在历史包袱里 从当前 V1 主线读
想读完所有注意力后端 广度换不到深度 选一个后端读透
只读论文不跑负载 缺少性能直觉 用 vllm bench serve 做实验
只读代码不读设计文档 重复造轮子 先扫 docs/design/
追新论文不动手 理解停留在名词 每个新概念找对应代码
O

小结

主线是代码，论文按需补给。顺序是：设计文档 → 一条请求的完整链路 → 调度与 KV cache → 一个分支方向。

判断标准只有一个：能不能解释一个具体现象，并预测改动后的影响。
