vLLM 的难点在哪里

六个核心矛盾，以及它们如何互相牵制

sourcevllm-project/vllm @ main

vLLM 难在耦合，不在单点。调度、显存、编译、并行各自都有成熟解法，拼在一起却会互相破坏假设。这篇文档按"矛盾"而不是"模块"来组织。

A

先看三个互相拉扯的目标

目标 想要 代价
吞吐 大 batch、长驻请求 首 token 延迟上升，显存紧张
延迟 小 batch、投机解码、异步调度 算力浪费，状态机变复杂
显存 多缓存、多预留、大 KV 池 更容易 OOM，淘汰更频繁
正确性 图优化、跨进程、跨实例 状态一致性难保证
核心矛盾

KV cache 是硬上限，请求长度是未知量。调度器每步都要在信息不全的情况下做分配。

B

难点一：调度器的在线决策

请求的最终长度未知，KV cache 却是硬上限。调度器每步只能按 token 预算做局部决策，同时兼顾吞吐、延迟和公平性。

KV 不足时只能抢占。被抢占的请求丢弃已算的 KV，回到等待队列，之后从头重算。前缀缓存能救回一部分进度，但命中率取决于请求分布。

异步调度再叠一层：GPU 还在算第 N 步，CPU 已经按"第 N 步会产出什么"的假设排第 N+1 步。假设不成立时，在途输出要丢弃。

代码入口：vllm/v1/core/sched/scheduler.py、async_scheduler.py。

C

难点二：异构的分页 KV cache

PagedAttention 只是起点。一个模型里可能同时有全注意力、滑动窗口、Mamba 状态、交叉注意力几套 KV 布局。每套的 block 大小和生命周期都不同。

前缀缓存要按 block hash 链复用。hash 的粒度、淘汰顺序、与抢占的交互必须一致。多模态请求还有 encoder cache，按 encoder 输出块管理。

任何一处记账错误都表现为显存泄漏或输出错乱。这类问题很难复现，因为依赖请求到达顺序。

代码入口：kv_cache_interface.py、kv_cache_manager.py、single_type_kv_cache_manager.py、block_pool.py。

D

难点三：多进程边界上的状态一致性

API Server、Engine Core、GPU Worker、DP Coordinator 各自是独立进程。中间是 ZMQ 和共享内存。

请求状态被拆到三个地方：API 侧负责分词与流式，引擎侧持有调度状态，Worker 侧维护输入状态。

abort、超时、进程崩溃、弹性扩缩容都要跨进程收敛。失败时不能只丢一个进程，否则 KV block 和请求队列会对不上。

代码入口：vllm/v1/engine/core.py、core_client.py、executor/multiproc_executor.py。

E

难点四：动态批处理 vs. 静态编译

CUDA Graph 要求 shape 固定，连续批处理每步的 batch 和序列长度都在变。

vLLM 的解法是 piecewise：decode 用完整 CUDA Graph，prefill 用分段图。图按 shape 分桶缓存，遇到新 shape 回退 eager。

难点在注意力这种数据依赖的算子上。图里不能有动态控制流，于是要把 attention 拆出图外，再用自定义 op 拼回去。

再叠加 torch.compile 的图断裂、显存池复用和编译时间，调优空间很大。

代码入口：vllm/compilation/、vllm/v1/worker/gpu_model_runner.py。

F

难点五：注意力后端与量化的组合爆炸

FlashAttention、FlashInfer、FlashMLA、Triton、Mamba/GDN、ROCm AITER，每个后端支持的 dtype、head size、KV 布局、mask 类型都不同。

选择器要按模型和硬件挑出可用组合，还要保证数值结果一致。

量化再乘一层：FP8、NVFP4、INT4，加上 KV cache 量化、per-head scale。每种组合都可能有精度或性能回退。

代码入口：vllm/v1/attention/selector.py、vllm/v1/attention/backends/、vllm/model_executor/layers/quantization/。

G

难点六：投机解码与结构化输出改写调度假设

投机解码一次验证多个 token。KV cache 要为可能被拒绝的 token 预留空间，接受率直接影响收益。

结构化输出把 grammar bitmask 的计算塞进调度器。采样前必须拿到 mask，异步调度下这又变成时序问题。

两者都会打破"一步一个 token"的简单模型。调度器要能表达"这一步可能产出多个 token"和"这一步还在等 mask"。

代码入口：vllm/v1/spec_decode/、vllm/v1/structured_output/。

H

两个广度型难点

模型覆盖：200+ 架构，包含 MoE、混合 SSM、多模态。统一构造签名解决了接口问题，但权重映射、层间差异、量化适配仍要逐个模型处理。

分离式服务：prefill、decode、encode 拆到不同实例。KV 要跨实例搬运，带宽、调度、故障处理都要重新设计。

I

难点之间的耦合

耦合对 冲突 典型表现
前缀缓存 × 抢占 释放的 block 能否复用 重算量增加，TTFT 抖动
异步调度 × 抢占 在途输出可能失效 需要主动丢弃输出
异步调度 × 投机解码 草稿 token 的时序假设 调度状态机复杂化
CUDA Graph × 连续批处理 shape 必须固定 分桶、回退 eager
投机解码 × KV cache 候选 token 要预留 显存放大，收益被抵消
结构化输出 × 异步调度 bitmask 与采样时序 等待状态难表达
DP × EP 负载均衡与专家分布 木桶效应
分离式 × 前缀缓存 KV 跨实例复用 传输成本高于收益

K

小结

vLLM 的架构几乎每处都在做取舍：吞吐 vs. 延迟、动态 vs. 静态、复用 vs. 隔离。

单个取舍都有解，难的是它们互相影响。读代码时先找"这个模块依赖了谁的假设"，比按目录顺序读更有效。
