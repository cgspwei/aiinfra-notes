vLLM 架构与源码学习路线

基于当前仓库 vllm-project/vllm main 分支的目录结构整理。所有路径均相对于仓库根目录，行号为撰写时的大致位置，随版本会漂移，请以函数名为准。

一句话主线 一个请求从 入口 → 引擎核心 → 调度器 → KV Cache 块分配 → Worker → 模型前向 → 采样 → 回传， 然后循环。只要把这个循环里每一步“谁负责、数据长什么样”弄清楚，vLLM 80% 的架构就清楚了。 其余 200+ 个模型文件、量化、LoRA、投机解码、CUDA kernel 都是围绕这条主线的“插件”。

学习原则

  1. 只看 vllm/v1/。这是当前引擎实现，旧版 V0 已不是主线。
  2. 先流程，后细节。每个文件第一遍只读类/函数签名和 docstring，不要逐行读。 scheduler.py 3700 行、gpu_model_runner.py 7100 行，从头读到尾是浪费。
  3. 带着问题读。每个阶段下面都给了“读完应能回答”的问题，答不上来就回头。
  4. 用调试器/日志串线。光读代码很容易迷路，用一个最小例子打断点走一遍（见动手与调试）。
  5. 优先读 docs/design/。官方设计文档比源码更适合建立整体图，再去源码里对号入座。
阅读时的心态 代码里充斥着 DP/EP/PP、KV connector、LoRA、多模态、ubatch、fault tolerance 等分支。 第一遍遇到这些分支一律当成“暂时为空”，只跟最朴素的路径：单卡、纯文本、不开任何高级特性。

三个自测问题

下面三个问题都能答个大概，就可以开始读源码了：

  1. 生成第 100 个 token 时，为什么不需要重新计算前 99 个 token 的 K 和 V？
  2. 多头注意力里，一个 [batch, seq, hidden] 的输入经过 QKV 投影后形状怎么变？
  3. 张量并行时，一个线性层的权重按行切和按列切，分别需要什么通信？

答不上来，说明 Transformer 推理这一块需要先补。推荐资料：

  • Andrej Karpathy 的 Let's build GPT（从零实现 GPT，约 2 小时）
  • vLLM 原论文（对 KV Cache 问题讲得很清楚）
  • The Illustrated Transformer（图解 Transformer）
建议：不要在前置知识上花太久 先补“必须有”的三项（已经具备就不用补），然后直接进入阶段 0–1，遇到不懂的概念再回头查。 vLLM 的概念密度很高，但每个都可以局部学习，没必要先成为 CUDA 专家再读。

阶段 0 · 先建立直觉（不看代码）

阶段 0

理解 LLM 推理的三个事实

必学建议 0.5–1 天

如果下面几个概念不清楚，读代码会一头雾水。

  • Prefill 与 Decode：prefill 一次处理整段 prompt（算力瓶颈）；decode 每次只生成 1 个 token（访存瓶颈）。
  • KV Cache：每个已处理 token 的 K、V 都要保存，显存占用随序列长度线性增长，是 LLM 服务的核心资源。
  • 为什么需要 PagedAttention 与 Continuous Batching：显存碎片 + 请求长度不一，静态 batch 利用率极低。

阅读材料

  • README.md、vLLM 论文（Efficient Memory Management for Large Language Model Serving with PagedAttention）
  • docs/design/paged_attention.md
  • docs/design/arch_overview.md（官方架构总览，最重要的一篇）
  • docs/design/prefix_caching.md
目标：能用自己的话画出“请求 → 调度 → 块分配 → 前向 → 采样”这张图。
读完应能回答：为什么 vLLM 要把 KV Cache 切成固定大小的 block？block 表和操作系统页表有什么类比关系？

阶段 2 · 调度器（最核心的一块）

阶段 2

Scheduler：continuous batching 的实现

必学建议 2–3 天

调度器决定 vLLM 的吞吐与延迟特性，也是社区改动最频繁、最值得理解的部分。

文件重点看什么
v1/core/sched/interface.py调度器接口，先看它定义了哪些方法（约 280 行）
v1/core/sched/output.pySchedulerOutput / NewRequestData / CachedRequestData：调度结果长什么样
v1/core/sched/request_queue.pywaiting 队列的策略（FCFS / 优先级）
v1/core/sched/scheduler.py schedule()（约 698 行）、_preempt_request()（约 1798 行）、update_from_output()（约 2252 行）

schedule() 的阅读顺序

  1. 先只看“running 队列”部分：已在跑的请求每步再分配几个 token、是否需要新 block；
  2. 再看“waiting 队列”部分：新请求如何查前缀缓存、分配 block、受 max_num_batched_tokens 限制；
  3. 然后看抢占：显存不够时谁被踢出、怎么回到 waiting；
  4. 最后看 chunked prefill：长 prompt 如何被切成多步处理，与 decode 混合同一批。

update_from_output() 同样重要：模型跑完后，它负责追加新 token、判断停止条件（EOS / max_tokens / stop string）、释放已完成请求的 block。

别被分支吓到 scheduler.py 里有大量 KV connector、编码器缓存、结构化输出、投机解码、DP 同步相关的分支。 第一遍遇到时扫一眼变量名、直接跳过。async_scheduler.py 和 diffusion_scheduler.py 也先不看。
目标：能手写一个 50 行的伪代码版 schedule()，包含 token budget、running/waiting 两个队列和抢占。
读完应能回答：V1 调度器为什么不再区分 prefill 阶段和 decode 阶段，而统一用“每个请求本步要算多少 token”来描述？

阶段 3 · KV Cache 管理（PagedAttention 的“内存管理器”）

阶段 3

KVCacheManager / BlockPool / 前缀缓存

必学建议 2 天
文件重点看什么
v1/kv_cache_interface.pyKV Cache 的规格描述（KVCacheSpec / KVCacheConfig）
v1/core/block_pool.py KVCacheBlock、空闲块队列、get_new_blocks()、free_blocks()、 cache_full_blocks()、get_cached_block()
v1/core/kv_cache_manager.py get_computed_blocks()（前缀命中，约 266 行）、allocate_slots()（分配，约 379 行）
v1/core/single_type_kv_cache_manager.py全注意力 / 滑窗 / Mamba 等不同层类型的块管理（先看 full attention 那一个类）
v1/core/kv_cache_utils.pyblock hash 计算（前缀缓存的关键）
docs/design/prefix_caching.md设计说明，建议与代码对着看

需要弄懂的几个机制：

  • block 是什么：固定 token 数（如 16）的 KV 存储单元；请求拥有一个“block 列表”，类似页表。
  • 引用计数 + LRU 空闲队列：block 被释放后不会立即清除，而是进入可被复用的队列，下次命中前缀可“复活”。
  • block hash：由“上一块 hash + 本块 token ids (+ 额外 key)”链式得到，实现跨请求的前缀共享。
进阶但不必现在读 kv_cache_coordinator.py、docs/design/hybrid_kv_cache_manager.md 处理“同一模型中不同层有不同注意力类型”的混合模型， 等主线通了再回来。
目标：能解释“两个请求共享相同 system prompt 时，第二个请求的 KV 是怎么被复用的”。
读完应能回答：为什么只有“填满的 block”才会被缓存？抢占一个请求时它的 block 会发生什么？

阶段 4 · Worker 与 ModelRunner（从调度结果到 GPU）

阶段 4

Executor → Worker → ModelRunner

必学建议 2–3 天
文件重点看什么
v1/executor/abstract.pyExecutor 抽象接口（约 500 行）
v1/executor/uniproc_executor.py单进程版，最简单，先看这个
v1/executor/multiproc_executor.py多卡张量并行的实际执行器，之后再看

v1/worker/gpu_input_batch.pyInputBatch：GPU 侧如何持久化一批请求的状态
v1/worker/block_table.py每个请求的 block 表如何落到 GPU 张量上

execute_model() 的核心逻辑

  1. _update_states：根据 SchedulerOutput 增删请求、更新 block 表；
  2. _prepare_inputs：把变长的多请求展平成一维 input_ids / positions / slot_mapping；
  3. _build_attention_metadata：生成 attention kernel 需要的元数据（seq_lens、block_table 等）；
  4. 调用模型 forward（可能被 CUDA Graph 包裹）→ 得到 hidden states；
  5. sample_tokens：取最后位置的 logits 并采样。
注意：存在两套 ModelRunner v1/worker/gpu_model_runner.py（7000+ 行，历史实现）和 v1/worker/gpu/model_runner.py（Model Runner V2，重构版）。 建议先读 docs/design/model_runner_v2.md 了解新旧关系；学习概念时先读旧版（资料多）， 读新版时重点看它如何把职责拆成更小的模块。
目标：能解释“为什么 batch 里的请求被展平成一维 token 序列，而不是 [batch, seq] 的二维张量”，以及 slot_mapping 的作用。
读完应能回答：vLLM 启动时是如何确定 KV Cache 能占多少显存、能开多少个 block 的？（提示：profile run）

2. 方便读懂流程的开关

  • enforce_eager=True：关闭 CUDA Graph 与编译，调用栈干净，便于断点。
  • VLLM_ENABLE_V1_MULTIPROCESSING=0：让 EngineCore 与前端同进程，可以直接用 pdb/IDE 单步（若当前版本仍支持，请以 vllm/envs.py 为准）。
  • VLLM_LOGGING_LEVEL=DEBUG：打印调度、块分配等日志。
  • tensor_parallel_size=1，关闭 prefix caching / chunked prefill 做第一遍，再逐个打开对比差异。

3. 推荐的 5 个断点

  1. LLM.generate —— 入口
  2. EngineCore.step —— 每一步的起点
  3. Scheduler.schedule —— 观察 SchedulerOutput 内容
  4. KVCacheManager.allocate_slots —— 观察 block 分配
  5. GPUModelRunner.execute_model —— 观察展平后的 input_ids 与 slot_mapping

4. 三个小实验

  1. 前缀缓存实验：连续发送两个共享长前缀的请求，观察第二次的 num_computed_tokens 与缓存命中日志。
  2. 抢占实验：把 gpu_memory_utilization 调得很低、并发调高，观察抢占日志。
  3. chunked prefill 实验：把 max_num_batched_tokens 调小，用长 prompt，观察 prefill 被拆成多步。

5. 配套的官方资料

  • docs/design/ 下的设计文档（本路线中已按阶段穿插）
  • docs/contributing/：贡献流程与 incremental_build.md
  • tests/v1/core/（调度器/KV 管理的单测）：测试往往是理解模块行为最快的方式
  • vLLM 官方博客：多篇文章讲解 V1 架构重构与各项特性
