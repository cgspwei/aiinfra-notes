PyTorch 构建系统深度解析

一条 pip install -e . 背后，是 Python 打包标准、CMake、Ninja、代码生成器、编译器、C++ ABI 和五种加速后端的协同。本文基于本仓库（version.txt = 2.16.0a0，HEAD 5a98911762f）的真实配置写成， 目标有两个：看懂 PyTorch 怎么构建，以及提炼出可用于设计同类多语言系统的经验。

先给结论 PyTorch 的构建系统不是一个工具，而是 七层职责明确的流水线： pip（驱动）→ scikit-build-core（适配）→ CMake（编排）→ torchgen（生成）→ Ninja（执行）→ clang/nvcc（编译）→ 安装布局（打包）。 每一层只解决一个维度的问题，层与层之间用标准接口（PEP 517、CMake cache、.ninja 依赖图）连接。 它复杂，但不混乱；这是本文最想让你带走的东西。

为什么值得研究

大多数项目的构建系统是「能跑就行」。PyTorch 的构建系统被迫解决一系列真实约束，这些约束在任何大型多语言项目里都会重现：

约束PyTorch 的应对可迁移性
两种语言、两种迭代速度（C++ 慢、Python 快）分层 + 可编辑安装的重定向模式任何 C++/Python、Rust/Python、Go/Python 混合项目
算子数量爆炸（数千个），且要跨 8 个后端YAML 单一事实来源 + 代码生成任何「大量同构接口」的系统（RPC、ORM、硬件抽象）
构建一次要几十分钟Ninja + ccache/sccache + 增量 + 并行度控制所有大型 C++ 项目
同一份代码要产出 pip wheel、libtorch、移动端、多平台构建选项矩阵 + 安装布局抽象任何多形态交付的产品
社区贡献者环境千差万别环境变量集中转发 + Summary 打印最终配置任何需要「用户自助排错」的开源项目
CI 要在几十种镜像上跑Docker 镜像内容哈希 + 统一构建脚本任何多平台 CI

全景：一次安装的 9 个阶段

这些阶段不是我总结的，是 CMakeLists.txt 开头的官方注释里写好的，顺序就是执行顺序：

1. Bootstrapforward toolchain env → project() → EnvVarForwarding.cmake
↓
2. Pre-buildcmake/PreBuildSteps.cmake — 子模块初始化与校验、拉取 pinned NCCL
↓
3. Options声明所有 USE_* / BUILD_* 开关（新增必须同步 Summary.cmake）
↓
4. Dependenciescmake/Dependencies.cmake — 找或建第三方库，配置 CUDA/ROCm/XPU 工具链
↓
5. Code generationtorchgen 生成 ATen 头/源；generate_code.py 生成 autograd 与 Python 绑定
↓
6. Main buildc10 → torch_cpu → torch_cuda/hip/xpu → torch → torch_python
↓
7. Export & extrasCaffe2Config.cmake / Targets；可选 binaries、JNI
↓
8. Python packagingFileMirroring、PackageData、PostBuildSteps（合并 compile_commands、头文件包装）
↓

读构建日志的正确姿势 -v 输出里，这 9 个阶段有清晰的边界。遇到失败先问：它死在第几阶段？ 第 1–4 阶段是「环境问题」，第 5 阶段是「schema/代码生成问题」，第 6 阶段是「代码问题」， 第 7–8 阶段是「打包/布局问题」。定位阶段比读最后一行报错有效得多。

分层与职责边界

L0 · 驱动pip
读取 pyproject.toml，按 PEP 517 调用构建后端，管理构建隔离，最后把产物装进环境。它不编译任何东西。
L1 · 适配scikit-build-core
把 CMake 包装成 PEP 517 后端：注入 SKBUILD_* 变量、把构建选项翻译成 CMake cache、生成 editable 重定向、组装 wheel。版本要求 >=1.1.1。
L2 · 编排CMake
发现依赖、声明选项、组织 target、生成构建文件、安装规则。真正的「构建系统」在这一层。入口 CMakeLists.txt。
L3 · 生成torchgen
用 Python 读 YAML，生成 C++ 头/源、Python 绑定、类型存根。它是构建的一部分，不是独立工具。
L4 · 执行Ninja
按依赖图并行调度编译与链接；复用 .o、记录 .ninja_deps、支持 ccache/sccache 包装。
L5 · 编译clang / gcc / nvcc / hipcc
把 C++/CUDA 变成目标文件。这一层的差异（ABI、C++ 标准、arch）是跨平台问题的主要来源。
L6 · 布局install rules
决定产物落在 torch/lib、torch/include，设置 rpath，包装 stable-ABI 头文件，组装 wheel。
边界为什么重要 PyTorch 的很多设计决定，本质是在维护这条边界：
· CMake 不负责「用户怎么安装」，只负责「产物长什么样」。
· pip 不知道 C++，只认 wheel 与 PEP 517 接口。
· torchgen 不参与编译，只产出可编译的文本。
· Ninja 不理解语义，只认文件依赖。
一旦某层越界（例如让 CMake 去猜 pip 的安装路径），系统就会变得脆弱。仓库里专门有断言防止这种越界（见下文 install-dir 的检查）。

pip 与 Python 打包标准

pip 到底做了什么

  1. 解析命令行与包元数据。
  2. （默认）创建构建隔离环境，安装 [build-system].requires。
  3. 调用 build-backend 的 build_wheel / build_editable。
  4. 拿到 .whl，解压到 site-packages，写 RECORD、direct_url.json。
  5. 解析并安装运行时依赖。

pip 是包管理器，不是构建系统。它只认 PEP 517 的三个钩子函数。PyTorch 把真正的构建全部藏在后端里。

相关的 Python 标准

构建隔离：为什么默认开，PyTorch 为什么要关

默认行为（隔离）

pip install .
# 1. 建临时 venv
# 2. 装 [build-system].requires
# 3. 在里面构建
# 4. 丢弃临时环境

优点：可复现、不受当前环境污染。缺点：每次重装依赖；看不到你环境里的 cmake/ninja/CUDA。

PyTorch 的选择（不隔离）

pip install -e . -v --no-build-isolation
# 直接用当前 venv
# 构建依赖必须预装

原因：numpy ABI 必须与运行时一致；要用环境里的 cmake/ninja/编译器/CUDA toolkit；构建太慢，无法承受重复装依赖。

代价要记住 关掉隔离后，pip 不会替你装那些依赖。缺 numpy、scikit-build-core、six 时， 报错发生在构建后端导入阶段，看起来和「编译失败」完全不同。这就是分层排错的意义。

editable 的三种实现，以及 PyTorch 为什么选第三种

方式做法问题
路径注入往 site-packages 放一个 .pth 指向源码目录只对纯 Python 有效；编译产物仍需另找位置
符号链接把包目录链到源码跨平台差；构建产物会污染源码树
重定向（redirect）安装一个 import hook：.py 指向源码，扩展模块指向持久构建目录实现复杂，但能同时满足「Python 热改」与「C++ 产物隔离」

PyTorch 的配置（pyproject.toml）：

[tool.scikit-build.editable]
mode = "redirect"
rebuild = false
rebuild-dir = "build/install/{wheel_tag}"

这里有两个值得学的决定：

  • 产物放进持久目录 build/install/{wheel_tag}。注释写明：否则每次安装都要把几 GB 压缩进 wheel 再解压，debug 构建要几分钟。
  • 不在 import 时自动重建。注释给了实测数据：否则每次 import torch 会跑约 7 次 cmake/ninja、多花约 25 秒。把「何时重建」的决定权交回给用户，而不是藏进 import。
设计启示 「开发态」和「发布态」是两种不同的产物，不应该共用一个安装模型。 开发态追求反馈延迟最小，发布态追求可分发、可复现。用 mode 开关区分，而不是靠文档告诉用户「记得重新装」。

pyproject.toml 逐段读

这个文件是整个构建系统的唯一入口。它大致分四块。

1. build-system：构建依赖的闭包

[build-system]
requires = [
  "numpy",
  "packaging>=24.2",
  "pyyaml",
  "scikit-build-core>=1.1.1",
  "typing-extensions>=4.15.0",
  "six",
]
build-backend = "scikit_build_core.build"

注释里有一条依赖链很值得注意：

NNPACK → PeachPy → six。PeachPy 在构建期生成 NNPACK 的热点汇编，且 import six。 NNPACK 默认开启（USE_NNPACK=ON），所以隔离构建也必须能拿到 six。

这说明构建依赖不是「随便列几个」，而是构建期代码路径的真实闭包。少一个，某条默认路径就会断。

2. tool.scikit-build：给适配层的指令

配置作用知识
minimum-version = "build-system.requires"版本下限跟 build requires 对齐避免两处版本漂移
build-dir = "build"构建目录持久化，增量构建的前提
install-dir = "torch"CMake 的 install prefix 落在 wheel 内的 torch/决定 torch/lib、torch/include 布局
strip = false保留符号torch.utils.cpp_extension 与 ABI 检查需要
packages = ["torch","torchgen","functorch"]打包哪些 Python 包不是「整个仓库」

3. env 与 overrides：配置翻译层

[tool.scikit-build.env]
CMAKE_BUILD_PARALLEL_LEVEL = { env = "MAX_JOBS" }
CC  = { env = "CC" }
CXX = { env = "CXX" }

[[tool.scikit-build.overrides]]
if.env.DEBUG = true
cmake.build-type = "Debug"

[[tool.scikit-build.overrides]]
if.env.REL_WITH_DEB_INFO = true
cmake.build-type = "RelWithDebInfo"

注意几个细节：

  • MAX_JOBS 是 PyTorch 的总并行度旋钮，被别名到 CMake 原生识别的 CMAKE_BUILD_PARALLEL_LEVEL。语义是 setdefault：用户显式设了后者就以后者为准。
  • 把 CC/CXX 列进 env 表，是为了关闭 scikit-build-core 的 sysconfig 编译器注入，避免 conda compiler_compat 或陈旧 venv 里的 gcc 干扰编译器探测。
  • cmake.build-type 故意不设默认值，让 CI 能通过环境变量传 RelWithAssert。
这是「配置的配置」 PyTorch 没有把 DEBUG 直接塞进 CMake，而是先用声明式规则翻译成 CMAKE_BUILD_TYPE。 好处是：用户只学一套环境变量，底层工具怎么变都不影响用户。

4. 一个 platform-specific override 的案例

if.platform-system = "win32"
cmake.define.CMAKE_GENERATOR = "Ninja"
env.CC = "cl"
env.CXX = "cl"

注释解释了原因：Windows 上默认用 Visual Studio 生成器，但它按 toolset 选编译器，会忽略 oneDNN-XPU 指定的 icx， 导致 oneDNN 用 MSVC 配置并失败。改成 Ninja 后，又要把宿主编译器钉死为 cl，否则 Intel oneAPI 环境里的 icx 会被误选去编译 CPU 代码，在 sleef 的 __float128 探测上翻车。

这类注释是构建系统里最值钱的东西：它记录的不是「怎么做」，而是「为什么不能那么做」。写构建代码时，一定要留下反例。

scikit-build-core 的角色

它是 CMake 与 Python 打包世界之间的协议转换器。职责可以概括成四件事：

职责具体行为
注入上下文设置 SKBUILD_PROJECT_NAME、SKBUILD_PROJECT_VERSION、SKBUILD_PLATLIB_DIR 等，供 CMake 读取
翻译配置把 [tool.scikit-build] 的字段变成 CMake cache 变量（cmake.define.*）
驱动构建依次执行 configure → build → install
组装产物把 install prefix 下的文件打进 wheel；editable 模式下生成重定向 hook

SKBUILD 变量如何影响 CMake

顶层 CMakeLists.txt 里有这样一段逻辑：

if(SKBUILD)
  get_filename_component(_torch_pkg_dir "${SKBUILD_PLATLIB_DIR}/torch" ABSOLUTE)
  get_filename_component(_torch_prefix "${CMAKE_INSTALL_PREFIX}" ABSOLUTE)
  if(NOT _torch_pkg_dir STREQUAL _torch_prefix)
    message(FATAL_ERROR ...)
  endif()
endif()

为什么必须相等？因为：

  • 扩展模块通过 $ORIGIN/lib（macOS 是 @loader_path）的 rpath 找 C++ 库；
  • torch/__init__.py 通过自己的 __file__ 找 bin/ 和 lib/；
  • 所以 install prefix 必须正好是 torch 包目录。

与其让错误在 import 时才暴露，不如在 configure 阶段直接 FATAL_ERROR。这是构建系统设计的黄金法则：把失败提前到最便宜的阶段。

注意：CMake 也能独立运行 CMakeLists.txt 的注释说明：正常由 scikit-build-core 驱动，例外是 tools/build_libtorch.py 的独立 libtorch 构建。 为此顶层对 SKBUILD_PROJECT_NAME/VERSION 提供了 fallback（从 version.txt 读）。 同一个 CMake 工程要能服务两种驱动方式，这是它保持可移植的关键。

CMake 的角色

1. 选项矩阵：所有开关集中声明

顶层 CMakeLists.txt 用 option() / cmake_dependent_option() 声明全部构建设置。节选：

option(BUILD_PYTHON "Build Python binaries" ON)
option(BUILD_TEST "Build C++ test binaries" ON)
option(BUILD_SHARED_LIBS "Build libcaffe2.so" ON)
cmake_dependent_option(USE_CUDA "Use CUDA" ON "NOT USE_TSAN" OFF)
option(USE_XPU "Use XPU" ON)
cmake_dependent_option(USE_ROCM "Use ROCm" ON "LINUX OR WIN32" OFF)
cmake_dependent_option(USE_CUDNN "Use cuDNN" ON "USE_CUDA" OFF)
option(USE_FBGEMM "Use FBGEMM" ON)
option(USE_KINETO "Use Kineto profiling library" ON)

三条规则值得学：

  1. 每个选项都要有默认值与说明，不能有「隐藏开关」。
  2. 依赖关系用 cmake_dependent_option 表达（例如 USE_CUDNN 只在 USE_CUDA 时有意义），而不是在脚本里写一堆 if。
  3. 新增选项必须同步 cmake/Summary.cmake。这条规则写在顶层注释里，是强制约定。否则用户无法确认自己的配置是否生效。

2. 环境变量转发：一个刻意收窄的接口

cmake/EnvVarForwarding.cmake 的规则写得很清楚：

一个环境变量会被转发为同名 CMake cache 变量，当且仅当它 (a) 以 BUILD_、USE_、CMAKE_ 开头， (b) 以 EXITCODE / EXITCODE__TRYRUN_OUTPUT 结尾， (c) 出现在 _ENV_ALIASES / _ENV_PASSTHROUGH / _LOW_PRIORITY_ALIASES 列表里。

这意味着：不是所有环境变量都能影响构建。想加新的配置面，必须显式登记，并在该文件里写文档。

为什么不自动全转发？ 环境变量是全局命名空间。自动转发会把 PATH、HOME、CI 系统的变量全灌进 CMake cache， 造成「本机能构建、CI 不能」的隐式耦合。显式白名单 = 可审计的配置面。

3. 依赖发现：找现成的，还是自己建

cmake/Dependencies.cmake 处理两类依赖：

  • 系统库：find_package 探测（BLAS、OpenMP、cuDNN、NCCL……），可用 USE_SYSTEM_* 控制。
  • 随仓库构建的库：third_party 子模块，用 add_subdirectory 或 ExternalProject 构建。

这里也是加速后端工具链的接线处：USE_CUDA 分支会 include cmake/public/cuda.cmake， 设置 CUDA 的 arch、编译选项、依赖库列表。

一个细节：NCCL 不是 git 子模块，而是默认（USE_SYSTEM_NCCL=OFF）在构建期按 pinned 版本 通过 FetchContent 拉取到 third_party/nccl（见 cmake/PreBuildSteps.cmake）； USE_SYSTEM_NCCL=1 时才改为链接系统安装的 NCCL。

4. target 拓扑：依赖是有向无环的

c10                    基础类型、Allocator、DispatchKey、TensorImpl
 └── torch_cpu        ATen CPU kernel、caffe2、autograd 引擎
      ├── torch_cuda   CUDA kernel（可选）
      ├── torch_hip    ROCm kernel（可选）
      └── torch_xpu    XPU kernel（可选）
           └── torch  伞形库（umbrella），统一链接
                └── torch_python   Python 扩展 _C.so（pybind11）
target定义位置职责
c10c10/CMakeLists.txt:48无上层依赖的基础库
torch_cpucaffe2/CMakeLists.txt:886CPU 算子与引擎
torch_cudacaffe2/CMakeLists.txt:1064CUDA kernel，按需构建
torchcaffe2/CMakeLists.txt:1013伞形 target，用 dummy 源文件承载链接关系
torch_pythontorch/CMakeLists.txt:307唯一的 Python 边界（_C.so）
为什么要有伞形库 下游 C++ 用户只想 find_package(Torch) 然后链接一个 torch，不想关心后端组合。 伞形 target 把「后端矩阵」封装成一个稳定名字。这是「对外的窄接口，对内的宽实现」。

5. 安装布局：rpath 是运行时契约

# cmake/Dependencies.cmake
if(APPLE)
  set(CMAKE_INSTALL_RPATH "@loader_path")
else()
  set(CMAKE_INSTALL_RPATH $ORIGIN)
endif()

配合 install-dir = "torch"，最终布局是：

torch/
├── __init__.py
├── _C.cpython-313-...so       # 扩展模块
├── lib/
│   ├── libtorch.so
│   ├── libtorch_cpu.so
│   ├── libtorch_cuda.so
│   └── libc10.so
└── include/
    └── torch/ ...

$ORIGIN/lib 让 _C.so 无需设置 LD_LIBRARY_PATH 就能找到同目录下的 lib/。 这个决定让 wheel 可以「解压即用」，也让 editable 重定向目录同样可用。

6. 编译期契约：ABI、符号与 stable API

  • C++ ABI：_GLIBCXX_USE_CXX11_ABI 必须与用户扩展一致，否则链接期出现难解的符号错误。
  • 符号保留：strip = false，因为 torch.utils.cpp_extension 与 CI 的 ABI 检查需要符号表。
  • Stable API 头包装：安装期运行 tools/wrap_headers.py，给头文件加上 TORCH_STABLE_ONLY / TORCH_TARGET_VERSION 守卫， 在用户定义这些宏时直接编译报错，而不是产生难查的运行时问题。
  • compile_commands.json：cmake/PostBuildSteps.cmake 会合并各子目录的编译数据库，供 clangd/工具链使用。

Ninja 与增量构建

Ninja 只做一件事：按依赖图尽快执行

CMake 负责「生成」build.ninja，Ninja 负责「执行」。它不理解语义，只看三样东西：

  • build.ninja：目标、规则、依赖边；
  • .ninja_log：每个目标的执行记录；
  • .ninja_deps：头文件依赖（gcc/clang 的 -MD 输出）。

所以「改一个头文件导致大面积重编」不是 Ninja 的错，是依赖图如实反映了代码耦合。

并行度：一个旋钮，三处生效

MAX_JOBS=14 pip install -e . -v --no-build-isolation
位置如何生效
CMake / Ninja[tool.scikit-build.env] 把 MAX_JOBS 映射为 CMAKE_BUILD_PARALLEL_LEVEL
cpp_extension JIT同样读 MAX_JOBS
第三方子构建NCCL / MKLDNN 等子构建也读它

另外 FLASH_ATTENTION_MAX_JOBS 单独控制 FlashAttention 的 CUDA 编译并发（CI 按 runner 内存设置）。

编译缓存：ccache / sccache

cmake_dependent_option(USE_CCACHE "Attempt using [S]CCache to wrap the compilation" ON "UNIX" OFF)

CMake 会自动找 ccache，找不到再找 sccache，并通过 CMAKE_*_COMPILER_LAUNCHER 包装编译器。 CI 里 ROCm 构建会显式设置 launcher。

增量构建什么时候失效 以下情况需要更彻底的重建：
· 改了 CMakeLists.txt 或 cmake/*.cmake → CMake 重新 configure；
· 改了 native_functions.yaml / derivatives.yaml → codegen 重跑，可能大量文件变化；
· 切换编译器 / Python 版本 / CUDA 版本 → 缓存与 ABI 都不再匹配；
· 改了 pyproject.toml 的构建相关字段 → 后端行为变化。

代码生成：torchgen

这是 PyTorch 构建系统里最具设计感的部分。它解决的问题是：几千个算子 × 8 个后端 × 3 种语言表面（C++ / Python / 类型存根）× 反向公式，靠手写不可能保持一致。

单一事实来源：native_functions.yaml

真实条目（aten/src/ATen/native/native_functions.yaml）：

- func: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  device_check: NoCheck
  structured_delegate: add.out
  variants: function, method
  dispatch:
    SparseCPU, SparseCUDA, SparseMPS, SparseMeta, SparseXPU: add_sparse
    SparseCsrCPU, SparseCsrCUDA, SparseCsrMeta, SparseCsrXPU: add_sparse_csr
    MkldnnCPU: mkldnn_add
    ZeroTensor: add_zerotensor
    Meta: add_Tensor_meta
    NestedTensorCPU, NestedTensorHPU, NestedTensorCUDA, NestedTensorXPU: NestedTensor_add_Tensor
  tags: [core, pointwise]

这一条声明同时生成了：

  • C++ 函数签名与 at::_ops::add_Tensor::call 的分发入口；
  • dispatch 注册表（哪个 key 走哪个 kernel）；
  • Python 绑定（torch.add、Tensor.add）；
  • 类型存根的输入（.pyi 由 tools/pyi/gen_pyi.py 从 .pyi.in 生成）；
  • autograd 接口（反向公式在 tools/autograd/derivatives.yaml）。

为什么用代码生成，而不是宏或模板

方案问题
C++ 宏错误信息不可读、调试困难、无法跨语言（Python 绑定生成不了）
手写模板几千个算子的重复代码无法维护
外部生成器（Python）生成物是普通 C++，可读、可搜索、可断点；生成逻辑本身可用 Python 快速迭代；能同时产出 C++/Python/stub
代价：生成物不能手改 所有 build/ 下的生成文件都是产物。改 .pyi 无效（要从 .pyi.in 生成）， 改 generated/*.cpp 无效（下次构建被覆盖）。单一事实来源的代价是「必须改源头」。

跨构建系统共享源清单

cmake/Codegen.cmake 里有一段非常有意思的代码：它把 build_variables.bzl 当 Python 执行，来提取源文件列表：

execute_process(COMMAND ${Python_EXECUTABLE} -c
  "exec(open('${PROJECT_SOURCE_DIR}/build_variables.bzl').read());
   print(';'.join([...]))")

原因：build_variables.bzl 同时被 Buck（Meta 内部构建）和 CMake（OSS 构建）使用。 如果在两处各维护一份源文件列表，必然漂移。用 Starlark 的语法子集当配置文件，两种构建系统都能读。

这是「跨工具链的单一事实来源」的典型手法：选一个双方都能解析的最简格式，而不是让一方去适配另一方的 DSL。

为什么矩阵没有炸掉

  1. 用选项组合，而不是复制代码树。同一份源码，靠 USE_* + dispatch key 决定编译哪些分支。
  2. 用 target 隔离。每个后端一个 target，链接关系清晰；伞形 torch 负责组合。
  3. 用 codegen 隔离。后端差异体现在 YAML 的 dispatch: 表里，而不是散落在手写代码中。
  4. 用 arch 列表控制产物大小。TORCH_CUDA_ARCH_LIST 决定为哪些 SM 架构生成代码；全架构会让二进制膨胀数倍。

子模块策略

cmake/PreBuildSteps.cmake 做三件事：

  1. 从 .gitmodules 读子模块路径；
  2. 如果全部缺失且存在 .git，自动执行 git submodule update --init --recursive；
  3. 校验每个子模块是否包含预期文件（CMakeLists.txt、LICENSE 等），防止「目录存在但为空」的坏检出。
为什么要在构建里做，而不是文档里写 文档会被跳过，构建不会。把「前置条件检查」放进构建流程，错误信息就能带着修复命令一起出现。 注意它只在 git checkout 下才尝试 init：源码 tarball 没有 .git，不能跑 git submodule。

CI 与可复现性

  • 环境即镜像：.ci/docker/ 下有 ubuntu、almalinux、manywheel、linter 等镜像定义，requirements-ci.txt 精确锁版本。
  • 镜像内容哈希：.ci/docker/ 的任何改动都会改变哈希，触发镜像重建。这是仓库的硬规则（见 CLAUDE.md），因为改一个 README 也可能让所有 CI 重新拉镜像。
  • 构建脚本统一：.ci/pytorch/build.sh 是入口，按 BUILD_ENVIRONMENT 分支（cuda / rocm / cpu / cuda13 …）。
  • 缓存：ROCm 用 sccache；CUDA 构建用 jemalloc 预加载规避已知问题；CUDA 13 关闭 FBGEMM。
  • 版本锚点：triton_version.txt、version.txt、submodule pin 共同定义「这次构建到底用了什么」。
可复现性的三要素 ① 输入可枚举（源码 + 子模块 + 依赖版本）； ② 工具链可标识（编译器、CMake、Ninja、CUDA）； ③ 配置可打印（Summary.cmake）。 PyTorch 三条都做了，所以 CI 失败可以「复现」，而不是「再跑一次试试」。

10 条可迁移的架构经验

这部分是本文的真正目的：把 PyTorch 的具体做法抽象成可复用的设计原则。

01

单一事实来源 + 生成器

做法：算子 schema、反向公式、源文件清单都只有一份，其余全部生成。

收益：一致性由机器保证，新增接口的成本从「改 8 处」变成「改 1 处 + 跑生成」。

代价：生成物不可手改，调试链路变长。适用：接口数量 > 50 且高度同构。

02

分层，且每层只依赖下一层的稳定接口

做法：pip 只认 PEP 517；scikit-build 只认 CMake；Ninja 只认文件依赖。

收益：任何一层可替换（setuptools→scikit-build、Make→Ninja），爆炸半径可控。

03

配置面必须显式、集中、可打印

做法：环境变量白名单 + option() 集中声明 + Summary 打印最终值。

收益：「为什么 CI 和本地不一样」变成可回答的问题。

04

开发态与发布态分离

做法：editable redirect vs wheel；两种产物、两条路径、同一个源。

收益：开发反馈快，发布产物干净。

05

把失败提前到最便宜的阶段

做法：configure 阶段断言 install prefix；构建前校验子模块；stable-ABI 头文件在编译期就报错。

收益：错误定位成本从「运行时 3 小时」降到「构建时 3 秒」。

06

增量与缓存是一等公民

做法：持久 build dir、Ninja、ccache/sccache、可选的 auto-rebuild。

收益：构建时间从 O(全量) 降到 O(改动)。

注意：缓存必须有明确的失效条件，否则会制造「幽灵 bug」。

07

矩阵用组合表达，不用分支复制

做法：USE_* 选项 × target × dispatch key，而不是为每个后端复制一棵源码树。

收益：N 个后端只需 O(N) 个开关，而不是 O(N) 份代码。

08

每层有自己的错误语义

做法：缺依赖、configure 失败、codegen 失败、编译失败、链接失败、安装失败，报错形态各不相同且可区分。

收益：排错从「读最后一行」变成「判断阶段」。设计错误信息时，先设计分类。

09

跨工具链共享清单

做法：build_variables.bzl 同时被 Buck 和 CMake 读取。

收益：避免「内部构建能过、开源构建不能过」的漂移。

手法：选双方都能解析的最简格式，而不是让一方适配另一方。

10

语言边界按「性能」与「迭代速度」划分

做法：性能关键路径用 C++/CUDA；编译器、生成器、胶水用 Python；边界收窄到一个 _C.so。

收益：既拿到性能，又保留快速迭代；边界少，ABI 与调试复杂度可控。

如果只能记一条 复杂系统不是靠「一个更强的工具」解决的，而是靠把复杂度切成互相独立、各自可验证的层。 PyTorch 的构建系统之所以能同时服务开发者、CI、wheel 用户、libtorch 用户和移动端， 是因为每一层都只回答一个问题，并且用标准接口把答案传给下一层。

动手实验

按顺序做，每个都能在 10–30 分钟内完成（构建本身除外）。

  1. 定位 9 个阶段。跑一次构建，在 -v 日志里标出每个阶段的开始行。写下你是靠什么特征识别的。
  2. 读 Summary。找到 ******** Summary ********，抄下 10 个关键值，解释每一个的来源（选项 / 环境变量 / 自动探测）。
  3. 加一个算子。在 native_functions.yaml 里加一个最简单的 op，重建，找到它在 build/aten/src/ATen/ 下生成了哪些文件。然后执行 git checkout -- aten/src/ATen/native/native_functions.yaml。
  4. 验证 editable 语义。改一个 torch/*.py 里的字符串，import 验证生效；再改一个 .cpp，验证不生效，然后重建验证生效。
  5. 并行度实验。分别用 MAX_JOBS=1、MAX_JOBS=14 构建一个小目标，记录 wall time 与 CPU 利用率。
  6. 缓存实验。装 ccache，做一次全量构建，再 touch 一个源文件重建，看命中率。
  7. 读构建图。ninja -C build -t graph | dot -Tsvg，找出 torch_python 到 c10 的路径。
  8. 制造一次 configure 失败。把 install-dir 改错，观察断言在哪一步触发、错误信息是否足够定位。
  9. 看 wheel。python -m build --wheel --no-isolation，解压 .whl，对照本文的安装布局，找出所有非 Python 文件。
  10. 构建 libtorch。BUILD_PYTHON=0，对比构建时间与产物大小，理解「关掉 Python 绑定」省掉了什么。

自测题

1. pip 和 CMake 各自负责什么？为什么不能合并？

pip 是包管理器与 PEP 517 驱动：解析元数据、管理隔离、调用后端、安装 wheel。CMake 是构建系统：发现依赖、生成构建图、组织 target。
不能合并：pip 要服务所有 Python 项目（纯 Python 项目根本不需要 CMake），CMake 要服务所有 C++ 项目（不关心 Python 打包）。合并会让两者都被迫理解对方的领域，失去可替换性。

2. --no-build-isolation 的收益与代价分别是什么？

收益：使用环境里真实的 numpy（ABI 一致）、cmake、ninja、CUDA toolkit；避免每次重复安装依赖。
代价：pip 不再自动安装 [build-system].requires，缺依赖时直接失败；构建不再可复现（受当前环境污染）。
结论：它把「可复现」的责任从工具转移给了用户/CI 镜像。

3. editable 的 redirect 模式解决了什么其他模式解决不了的问题？

它同时满足两个互相冲突的需求：Python 文件要能热改（指向源码树），C++ 产物要能隔离且持久（指向 build/install/{wheel_tag}）。
路径注入只能处理纯 Python；符号链接会让构建产物污染源码树；复制则失去「可编辑」的意义。
另外它默认关闭 import 时重建，避免每次 import torch 触发 cmake/ninja。

4. 为什么 install prefix 必须等于 <platlib>/torch？

因为运行时定位依赖它：扩展模块通过 $ORIGIN/lib（macOS @loader_path）的 rpath 找 C++ 库；torch/__init__.py 通过自身 __file__ 找 bin/ 与 lib/。prefix 不一致会导致「构建成功、import 失败」。
所以 CMake 在 configure 阶段直接 FATAL_ERROR，把失败提前。

5. 为什么 PyTorch 用 YAML + 代码生成，而不是 C++ 宏？

宏无法跨语言（生成不了 Python 绑定与 .pyi）、错误信息差、调试困难、几千个算子的组合会失控。
YAML 是单一事实来源，生成器可以用 Python 快速迭代，产物是普通可读 C++。
代价：生成物不可手改，必须改源头。

6. build_variables.bzl 为什么被 CMake 当 Python 执行？

因为它要同时服务 Buck 和 CMake 两套构建系统。它本质是 Starlark，但语法是 Python 的子集，所以 CMake 可以用 exec(open(...).read()) 读取其中的列表。
目的：避免两套构建系统各自维护源文件清单而产生漂移。手法：选双方都能解析的最简格式。

7. 环境变量转发为什么用白名单，而不是全转发？

环境变量是全局命名空间。全转发会把 PATH、HOME、CI 变量等灌进 CMake cache，造成隐式耦合与不可复现。
白名单（BUILD_*、USE_*、CMAKE_* + 显式别名）让配置面可审计，新增开关必须登记并写文档。

8. 为什么新增一个 CMake 选项必须同时改 Summary.cmake？

因为用户需要确认「我的配置是否真的生效」。如果选项存在但不出现在构建摘要里，用户只能靠猜。
这是可观测性要求：所有影响产物形态的配置，都必须能在构建结束时被打印。

9. 改哪些文件会让增量构建失效？

CMakeLists.txt / cmake/*.cmake（重新 configure）、native_functions.yaml / derivatives.yaml（codegen 重跑）、pyproject.toml 的构建字段、编译器/Python/CUDA 版本变化（缓存与 ABI 不匹配）。
改头文件也会触发依赖它的源文件重编——这是依赖图的正确行为，不是缓存失效。

10. 如果让你设计一个「Python 前端 + Rust 核心」的系统，会借鉴哪几条？

① 用 PEP 517 后端（如 maturin）做薄适配层；② 开发态用 editable redirect，发布态出 wheel；③ schema 单一事实来源 + 生成绑定；④ 配置面白名单 + 构建摘要；⑤ 每个 target 独立，伞形库封装后端矩阵；⑥ 错误按阶段分类；⑦ 缓存有明确失效条件；⑧ 语言边界收窄到一个扩展模块。
核心不是照搬工具，而是借用分层与契约的设计。
