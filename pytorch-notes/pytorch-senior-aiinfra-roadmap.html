PyTorch 深度学习路线

目标：达到 Google / OpenAI AI Infra 资深工程师（L5 / Senior）的实际工作能力，而不是「会调 torch.compile」。 文中源码路径均基于本机仓库 pytorch/pytorch（HEAD 5a98911762f，2026-11）实测存在；引用函数名而非行号，避免版本漂移。

一句话主线 一个 tensor 从 Python 表达式出发，依次穿过 Dispatcher → Autograd → 编译栈（Dynamo/AOTAutograd/Inductor）→ GPU kernel → 集合通信 五层。 资深工程师和普通使用者的差别不是「知道这五层存在」，而是任何一层出问题，能在 30 分钟内定位到具体一层、给出证据、并修掉。 整份路线就是把这五层逐层打通，再用分布式与推理两个真实系统把它们串起来。

怎么用这份路线

三条硬规则

  1. 每个阶段必须有可运行产物。没有 lab 的阶段等于没学。路线里每个阶段都给了「验收标准」，全部带勾选框。
  2. 先 profiling 后结论。任何性能判断都要有 ncu / nsys / torch.profiler 的数字支撑，禁止「我觉得」。
  3. 读源码用「假设—验证」法。先猜这段代码怎么工作，再打断点/加日志验证；禁止从第一行顺序读到大结局。

不做什么

  • 不刷教程视频。以源码、论文、官方 dev-discuss 为主，视频只在卡住时看。
  • 不追求学完再动手。阶段 2 和阶段 3 本身就要求交叉进行。
  • 不在没有 GPU 的机器上死磕 kernel。见 算力与环境。
  • 不把「读完」当里程碑。里程碑只有：跑通、测出数字、解释清楚、提交 PR。
关于「资深」的诚实说明 PyTorch 是底座，不是全部。senior AI Infra 的能力 = 框架内部理解 × 系统设计 × 性能工程 × 协作影响力。 这份路线按 约 15 小时/周、36 周设计（约 540 小时）。全职投入（35–40h/周）可压缩到 4–5 个月。 低于 8h/周建议把周期乘以 2，否则 lab 会退化成「看一遍代码」。

阶段 1 · Tensor / Dispatcher / Autograd（3 周）

01

一个 tensor 到底经过了什么

周期3 周 · 45h
前置阶段 0
产出1 个完整自定义算子 + 1 篇调用链笔记

建立「任何 Python 表达式都能拆成 5 层」的心智模型。这一层不透，后面所有调试都是猜。

必须建立的心智模型

  • Tensor 是 3 个东西的组合：TensorImpl（元数据：sizes、strides、storage_offset、DispatchKeySet、autograd meta）+ Storage（真实内存）+ 一个 dtype/layout 标签。view 只改元数据，contiguous() 才分配内存。所有「为什么这个 op 慢」的问题，先问 stride。
  • Dispatcher 是按 key 查表：一次调用先算 DispatchKeySet（backend key + functionality key，如 AutogradCPU、Functionalize、Python、Meta、Fake），再按优先级找第一个注册的 kernel，找不到走 fallback。理解优先级顺序，就理解了「为什么 autograd 包在外面、functionalization 包在里面」。
  • schema 是契约：native_functions.yaml 里的 dispatch: 决定每个 backend 实现什么；CompositeImplicitAutograd 表示「这个 op 由别的 op 组合而成，autograd 自动可用」。这决定了你新加算子该写 C++ kernel 还是写 decomposition。
  • Autograd 是反向图 + 引擎：前向时每个 op 的 Node 通过 next_edges 连成 DAG；反向时引擎把「入度归零」的节点放进 ready queue 并行执行。SavedVariable 保存反向需要的张量，版本计数器保证 in-place 安全。
  • functionalization 把可变 op 变成不可变：编译栈要求图无副作用，所以 add_ 会被改写成「读 + 写回」。这是理解 Inductor 图和 torch.export 的前提。
  • view / alias 是一等公民：ViewAndMutationMeta 记录了哪些输出是输入的别名，这直接影响 AOTAutograd 能否安全地重排、以及 FSDP 能否原地 reduce-scatter。

Lab

  1. 调用链追踪。对 torch.nn.functional.layer_norm 做一次完整追踪：Python → _C._VariableFunctions → dispatcher → AutogradCPU kernel → CPU kernel。用 TORCH_SHOW_DISPATCH_TRACE=1 与 torch._C._dispatch_dump_table("aten::layer_norm") 交叉验证。产出一张图。
  2. 手写完整算子。实现 myops::fused_scale_add(Tensor x, Tensor y, float a, float b) -> Tensor：CUDA kernel + CPU 参考实现 + Meta 实现 + autograd（用 torch.library 或 derivatives.yaml）+ decomposition（给 Inductor 用）+ 测试（instantiate_device_type_tests、gradcheck）。要求它能被 torch.compile 正常编译。
  3. autograd 解剖。构造 y = (x @ w).relu().sum()，打印 y.grad_fn 及其 next_functions 递归结构；用 torch.autograd.set_multithreading_enabled(False) 对比执行顺序；解释 SavedVariable 保存了什么、为什么 relu 只需存 output。
  4. in-place 报错复现。复现 "a view of a leaf Variable that requires grad is being used in an in-place operation"，从 VariableVersion / version_counter 的角度解释。
  5. 写一个 tensor subclass。用 __torch_dispatch__ 实现一个「记录所有 op 调用 + 统计 FLOPs」的包装张量。这是理解 subclass 机制与 torch function mode 的最快路径。
  6. functionalization 观察。用 torch._enable_functionalization() 或 Inductor 日志观察 add_ 如何被改写；说明为什么编译器需要它。

常见误区

① 一上来逐行读 engine.cpp 3000 行——应该先读 GraphTask 结构和 execute_with_graph_task 主循环，其余按需。
② 以为 autograd 是「记录操作序列」——它是 DAG + 引擎，且反向可以被多次触发（retain_graph）。
③ 以为 contiguous() 总是拷贝——已经连续时是 no-op，这正是很多「优化无效」的原因。
④ 新算子只写计算 kernel，忘了 meta / fake / decomposition，结果 torch.compile 直接 graph break。

阶段 2 · torch.compile 全栈（6 周）

02

Dynamo → AOTAutograd → Inductor → export/AOTI

周期6 周 · 90h
前置阶段 1
产出lowering + template + 一份编译报告

这是整条路线最值钱的一段。能做到「给定任意模型，说清它被编译成了什么、为什么这么编译」，就已经超过大多数使用者。

2.1 Dynamo：图捕获

  • 机制：通过 CPython 的 frame evaluation hook（PEP 523）接管字节码执行，把 Python 字节码逐条翻译成 FX 图；遇到无法静态化的操作就 graph break，回退到 eager。
  • VariableTracker：Dynamo 不执行真实 Python 对象，而是对 VariableTracker 抽象解释。TensorVariable、SymNodeVariable、UnspecializedPythonVariable 的区别决定了何时特化、何时泛化。
  • Guards：每个编译产物绑定一组守卫（类型、id、shape、值）。守卫失败即 recompile。理解 guard 就理解了「为什么改个 batch size 就变慢」。
  • 动态 shape：automatic_dynamic_shapes 在第二次遇到不同 shape 时把该维标记为 SymInt；assume_static_by_default、specialize_int 决定特化粒度。动态 shape 会带来额外的 guard 与 kernel 分支。
  • HOPs：torch._higher_order_ops（cond、while_loop、scan、flex_attention、invoke_subgraph）让控制流与 attention 保持在图内。

2.2 AOTAutograd：前向 + 反向一起编译

  • 把 forward 图与 autograd 结合，生成 joint graph，再用 min-cut partitioning 切成 forward / backward 两张图。
  • 切分点决定「哪些中间结果要存、哪些要重算」。这就是 activation checkpointing 在编译栈里的自然表达（torch.utils.checkpoint 会变成 tag_activation_checkpoint HOP）。
  • ViewAndMutationMeta 记录所有输入输出的 alias / mutation，是正确性的核心。
  • AOTAutogradCache：按图 + 配置缓存编译结果，避免重复编译。

2.3 Inductor：从图到 kernel

  • Lowering：FX 节点 → IR（TensorBox/StorageBox/Loop/Pointwise/Reduction/Scan/ExternKernel）。先查 decomposition 表，把复合算子拆成基础算子。
  • Scheduler：决定 fusion、realize、内存复用。融合的判据是「能否在同一个 loop 里完成且不重复计算」，不是「看起来能合就合」。理解 SchedulerNode 的依赖边与 why_fused。
  • Codegen：Triton（GPU）/ C++（CPU）/ Metal。看 codegen/triton.py 如何生成 tl.load/tl.store/mask/索引表达式。
  • 模板与 autotune：matmul、attention 等走 select_algorithm.py + TritonTemplate，对 tile size / num_warps / num_stages 做搜索，结果写入 autotune cache。
  • Epilogue fusion：mm + bias + activation 合成一个 kernel；kernel/mm.py 展示了 prologue/epilogue 的组合方式。
  • CUDAGraphs：cudagraph_trees.py 用内存池 + 静态输入消除 launch overhead。约束：shape 固定、不能有 CPU 同步、不能动态分配。
  • 缓存：FxGraphCache（图级）、TritonFuture（异步编译）、codecache.py（磁盘产物、打包）。冷启动优化全靠这一层。

2.4 export 与 AOTI

3.1 硬件模型（必须先建立）

  • 执行模型：grid → block（CTA）→ warp → thread；SM 内 warp scheduler、寄存器文件、shared memory/L1；occupancy 决定能否掩盖延迟。
  • 内存层级：寄存器 → shared memory → L2 → HBM。合并访问（coalescing）、bank conflict、L2 命中率决定有效带宽。
  • Roofline：算术强度 = FLOPs / Bytes。低于拐点就是 memory-bound，优化方向是减少访存或提高复用；高于拐点才谈 tensor core 利用率。
  • Hopper 特性：TMA（cp.async.bulk.tensor，异步多维拷贝，不占寄存器）、thread block cluster + distributed shared memory、warp specialization（producer/consumer）、异步事务屏障 mbarrier。
  • Blackwell：第五代 tensor core、FP4/FP6、更大 SM 内共享内存，kernel 设计进一步走向「TMA + warp specialization + 持久化」。
  • 数值：BF16/FP16 → FP32 accumulate；FP8 e4m3（权重/激活）vs e5m2（梯度）；per-tensor / per-channel / per-block scaling；delayed scaling；stochastic rounding。数值错误往往表现为「loss 缓慢漂移」，不是 NaN。

3.2 Triton 深入

  • block-level 编程模型、tl.load/store 的 mask 与 other、make_block_ptr、descriptor（TMA）。
  • layout 与 num_warps/num_stages：软件流水线的本质是「预取下一块 + 计算当前块」，stage 数就是缓冲区深度。
  • tl.dot / tl.dot_scaled；reduce 与 tl.associative_scan（实现 cumsum/softmax）。
  • 持久化 kernel（persistent）：减少 launch 与 tail effect，配合 stream-K 解决 GEMM 的 wave quantization。
  • 自动调优：triton.autotune、config 空间设计、缓存复用。

3.3 GEMM 与 Attention

  • GEMM：分块（tile）、寄存器分块、双缓冲、split-K、stream-K、epilogue fusion、TMA、warp specialization。目标是逼近 cuBLAS/CUTLASS。
  • CUTLASS/CuTe：理解 tile 层级（CTA / warp / MMA）、layout 代数、epilogue 访存；不必从零写，但要能读 third_party/cutlass 的 kernel 结构。
  • Attention：online softmax、分块避免 materialize N×N、GQA/MQA 的 KV 复用、causal mask 的块级跳过、FlashDecoding 的 split-KV、PagedAttention 的间接寻址、MLA 的低秩压缩。
  • FlexAttention：用 block mask 表达任意稀疏模式，理解 torch/nn/attention/flex_attention.py 的 score-mod 与 mask 语义。

05

从 KV cache 数学到 serving engine

周期6 周 · 90h
前置阶段 3；阶段 4 的 TP 部分
产出mini serving engine + SLO 报告

能对一个 LLM 服务做容量规划：给定模型、SLO、硬件，算出需要几张卡、多少 batch、瓶颈在哪。

5.1 第一性原理

  • 两阶段：prefill 是 compute-bound（大矩阵乘），decode 是 memory-bound（每步只算 1 个 token，但要读全部权重 + KV）。
  • KV cache 公式：2 × layers × kv_heads × head_dim × seq_len × batch × dtype_bytes。例：Llama-3-70B（80 层、8 KV heads、128 dim、8192 ctx、batch 32、fp16）≈ 86 GB。这个数字决定了一切。
  • decode 延迟下界：每步需读 权重 + KV 字节，除以 HBM 带宽。70B bf16 权重 140GB，H100 3.35TB/s → 单步理论 > 42ms（不含 KV）。这就是为什么 decode 必须靠 batch 摊薄。
  • 指标：TTFT（首 token 延迟）、TPOT/ITL（token 间延迟）、吞吐（tokens/s）、goodput（满足 SLO 的吞吐）。优化目标不同，方案完全不同。

5.2 关键技术

  • PagedAttention：KV 按 block 管理，block table 做逻辑→物理映射；消除碎片、支持共享前缀、支持按需增长。
  • Continuous batching：以 iteration 为调度单位，请求完成即退出、新请求即加入；配合 chunked prefill 避免长 prefill 阻塞 decode。
  • Prefix caching：按 block hash 复用相同前缀的 KV，对多轮对话/系统提示收益巨大。
  • Attention 后端：FlashAttention / FlashInfer / cuDNN / TRT-LLM / flex_attention；不同后端在不同 seq/batch 下差异明显，必须实测。
  • 投机解码：draft model / Medusa / EAGLE / MTP / n-gram；加速比 ≈ (1 + α·k) / (1 + c)，α 是接受率、k 是草稿长度、c 是草稿成本。接受率是命门。
  • 量化：W8A8、W4A16、FP8（per-tensor / per-channel / per-block）、MXFP4/NVFP4；torchao、torch._scaled_mm。必须同时测精度与延迟。
  • 并行：TP（每层 all-reduce）、EP（MoE all-to-all）、DP 副本；P/D 分离（prefill 与 decode 分池，KV 通过 NIXL/Mooncake 传输）以独立扩缩容。
  • 调度：优先级、SLO 感知、chunked prefill 的 chunk 大小、max_num_seqs、max_num_batched_tokens。
  • 执行优化：CUDA graph（decode 形状固定，收益极大）、torch.compile、AOTI、piecewise CUDA graph。

MFU、优化器、容错与集群

周期5 周 · 75h

核心概念

  • MFU：6 × N × D / (t × peak_FLOPs)。H100 bf16 稠密峰值约 990 TFLOPS（SXM，含 sparsity 翻倍）。好的训练 MFU 在 35–55%。MFU 是唯一能横向比较训练系统的指标。
  • Scaling law：Chinchilla 的 compute-optimal 配比；muP 用于超参迁移；这些决定「给定算力该训多大模型、多少 token」。
  • 优化器显存：AdamW 每参数 4（fp32 master）+ 4（m）+ 4（v）+ 2（bf16 param）+ 2（bf16 grad）= 16 bytes；Muon / 8-bit optimizer 可显著降低。
  • 激活重计算：全量 checkpoint 约省 O(√L) 显存、多 33% 计算；选择性 checkpoint 只对 attention 部分重算，性价比最高。
  • 数据管线：tokenizer、packing（避免 padding 浪费）、去重、流式读取、多 worker 预取、样本级 shuffle buffer。数据瓶颈常被误判为 GPU 瓶颈。
  • 容错：torchrun --max-restarts、周期性 checkpoint、异步 checkpoint、straggler 检测、节点健康检查。
  • 集群：NVLink 域（8 卡）→ IB rail-optimized 拓扑 → GPUDirect RDMA；NCCL 拓扑探测；gang scheduling；拓扑感知放置。
  • 稳定性：loss spike 的常见原因（LR 过大、bf16 溢出、数据脏、通信不同步、优化器状态异常）；如何用 grad norm、activation norm 定位。

  2. 扩展性曲线。1 → 2 → 4 → 8 卡，画吞吐与 scaling efficiency；解释每段下降的原因（通信、数据、bubble）。
  3. 重计算策略。对比 none / selective / full 的显存与吞吐，给出最优选择及理由。
  4. 优化器对比。AdamW vs 8-bit vs Muon，在相同 token 预算下比较 loss 与显存。
  5. 故障注入。训练中 kill 一个 rank，验证弹性重启 + checkpoint 恢复，测恢复时间与丢失步数。
  6. loss spike 诊断。人为制造一次（调大 LR / 注入异常数据），用 grad norm、per-layer norm、数据回放定位。
  7. 成本分析。给定预算与目标 loss，估算所需 GPU-hours 与最优模型规模。

自测题库

每题都要能给出「结论 + 推导 + 边界条件」。答不上来，回到对应阶段。

1. x.t() 为什么不产生 kernel？y = x.t() + 1 会产生几个 kernel？

结论：t() 只改 stride 元数据，零拷贝、零 kernel。y 通常 1 个 kernel（Inductor 可把转置融合进 pointwise 的索引表达式），eager 下也是 1 个 kernel。
推导：TensorImpl 的 sizes/strides 是可变量；t() 返回新 TensorImpl 共享 Storage。+1 是 pointwise，逐元素读写，访存量 2×N×dtype。若下游需要连续内存（如 GEMM 输入），才会插入 copy kernel。
边界：若后端不支持非连续访存（某些 kernel 要求 contiguous），会隐式 contiguous()，这时才是 2 个 kernel。

2. 为什么 torch.compile 在 batch size 变化时会重新编译？

结论：Dynamo 默认对 int 参数做特化并生成守卫，形状变化导致守卫失败，触发 recompile；开启 automatic_dynamic_shapes 后第二次不同 shape 会把该维转为 SymInt。
推导：guard 绑定具体值或 SymInt 的约束；cache_size_limit 限制单码对象的缓存条目。
边界：动态 shape 会增加守卫和 kernel 分支，短序列/小 batch 场景可能反而更慢；用 mark_dynamic + Dim 约束可减少分支。

3. 列举 5 种常见 graph break 原因。

① 数据依赖的控制流（if x.sum() > 0）；② 调用未支持的第三方库 / C 扩展；③ .item()、.data_ptr() 等需要具体值的操作；④ 动态创建的 Python 对象 / 副作用；⑤ 不支持的自定义 autograd.Function；⑥ 张量作为 dict key / 依赖 id()。（答 5 个即可）

4. 为什么编译区域内调用 loss.item() 很糟？

结论：它要求 GPU→CPU 同步取值，打断图、强制同步、阻止融合与 CUDA graph。
推导：.item() 产生 unbacked SymInt / 需要真实数据，Dynamo 只能 graph break；即使不断图，也会插入 sync，破坏异步流水。
做法：把 logging 放到图外；必须在图内就用 torch._dynamo.graph_break() 显式隔离，或累积到 device 上定期取。

5. 解释 min-cut partitioning，以及为什么反向需要重算。

结论：AOTAutograd 把 forward 与 backward 合成 joint graph，再找一组割点把图切成两半：割点上的张量被保存，其余中间结果在反向时按需重算。
为什么重算：保存所有中间激活显存不可承受；重算用计算换显存。min-cut 在「保存字节数」与「重算计算量」之间优化。
边界：重算会增加约 33% 计算（全量 checkpoint 的最坏情况），但可通过选择性 checkpoint 降低。

6. Functionalize dispatch key 解决什么问题？

结论：把带副作用/别名的 op（add_、copy_、resize_）改写成纯函数式形式（读旧值 + 产生新值 + 写回），使图可以被安全地重排、融合、并行。
为什么需要：编译器要求无隐藏状态；分布式要求明确的读写依赖；export 要求纯函数。
边界：functionalization 会增加拷贝，Inductor 会在 lowering 阶段再消掉不必要的拷贝。

7. 为什么 FakeTensor 跑不了 torch.nonzero 的某些用法？

结论：nonzero 的输出形状依赖数据，FakeTensor 没有数据，只能产生 unbacked SymInt；后续若用它做索引/切片，就可能无法求解约束而报错。
处理：用 constrain_range、改写算法、或接受 graph break。
边界：unbacked SymInt 不是错误，关键是不要让它参与需要具体值的运算。

8. Inductor 如何决定两个 op 是否融合？

结论：看它们能否在同一个 loop nest 内完成，且不增加重复计算或破坏依赖；同时考虑 realize（是否必须物化）、内存复用、以及 reduction/scan 的不可融合性。
证据：SchedulerNode 的依赖边、why_fused 日志、生成的 kernel 数。
边界：融合不是越多越好：过度融合会增加寄存器压力、降低 occupancy。

9. DDP 的 bucket 大小如何取舍？

结论：bucket 越大，单次 all-reduce 效率越高（摊薄延迟），但开始通信越晚、与反向重叠越少；bucket 越小，重叠越好但通信次数多、延迟占比高。
调法：从 25MB 起，用 nsys 看「all-reduce 覆盖反向的比例」，画曲线找拐点。
边界：gradient_as_bucket_view 可省一次拷贝；static_graph 允许更激进的优化。

10. FSDP2 与 FSDP1 的关键区别？

结论：FSDP2 用 DTensor 对每个参数独立分片（dim 0），不再把所有参数压成一个 FlatParameter；因此支持按参数设置不同策略、更好的 TP 组合、更清晰的 state dict、更少的内存峰值。
代价：通信次数可能更多，需要 collector 做批处理。
边界：小参数很多时，collector 的批处理策略直接影响性能。

11. 为什么 FSDP 在 forward 前 all-gather、backward 后 reduce-scatter？

结论：参数按 dim 0 分片存储以省显存；计算需要完整参数，所以 forward 前 all-gather，用完即释放（reshard_after_forward）；反向得到的是完整梯度，需要 reduce-scatter 回分片形式，同时完成梯度同步。
显存账本：峰值 ≈ 分片参数 + 当前层的完整参数 + 激活 + 梯度分片。
边界：reshard_after_forward=False 省一次 all-gather，但显存峰值升高。

12. 7B 模型用 AdamW + bf16 混合精度，不切分需要多少显存？

结论：参数 bf16 14GB + 梯度 bf16 14GB + fp32 master 28GB + Adam m/v 56GB ≈ 112GB，再加激活。单卡 80GB 放不下。
推导：每参数 2+2+4+4+4 = 16 bytes × 7e9。
边界：8-bit optimizer 可把 m/v 降到 14GB；ZeRO/FSDP 按卡数分摊。

13. 推导 ring all-reduce 的通信量。

结论：每卡发送/接收约 2(N-1)/N × S 字节（reduce-scatter + all-gather 各 (N-1)/N × S）。
含义：N 很大时趋近 2S，与卡数基本无关；因此增大规模时通信量不爆炸，但延迟和带宽竞争会。
边界：tree 算法在小消息/高延迟网络下更优；NVLink 域内可用更激进的算法。

14. TP、PP、DP 分别在什么情况下用？

DP：模型放得下、追求吞吐，通信是梯度 all-reduce，最成熟。
TP：单层放不下或需要降延迟，通信是每层 all-reduce，必须高带宽（NVLink 域内）。
PP：超大规模、跨节点，通信量小但有 bubble，需要足够 micro-batch。
组合原则：TP 放节点内，PP 跨节点，DP 最外层；EP 用于 MoE。

15. 为什么 decode 是 memory-bound？给出延迟下界公式。

结论：每生成 1 个 token，需要读取全部权重 + 该请求的 KV cache，但只做 O(1) 的矩阵-向量计算，算术强度极低。
下界：t ≥ (W_bytes + KV_bytes) / HBM_BW。70B bf16 权重 140GB / 3.35TB/s ≈ 42ms。
推论：提高 batch 可摊薄权重读取，但 KV 线性增长；因此需要 PagedAttention、量化、投机解码。

16. 算一下 Llama-3-70B、8192 上下文、batch 32、fp16 的 KV cache。

结论：约 86GB。
推导：2（K/V）× 80 层 × 8 KV heads × 128 dim = 163,840 元素/token；×8192 = 1.34e9；×32 = 4.29e10 元素；×2 bytes ≈ 85.9GB。
边界：GQA 已经把 KV heads 从 64 降到 8；若用 MLA 或 KV 量化还能再降。

17. PagedAttention 相比连续 KV 分配的三个收益？

① 消除外部碎片（按 block 分配，浪费 < 1 block/请求）；② 支持前缀共享（block table 指向同一物理块，copy-on-write）；③ 支持按需增长与抢占（可换出/重算），提升并发。
代价：间接寻址增加 kernel 复杂度，需要专门的 attention 实现。

18. Chunked prefill 解决什么问题？

结论：长 prefill 会独占一个 iteration，导致正在 decode 的请求 TPOT 抖动（尾延迟恶化）。把 prefill 切成小块与 decode 混批，可平滑 TPOT。
代价：prefill 的 TTFT 可能变长；chunk 太小会降低 prefill 的算力利用率。
调法：按 SLO 调 max_num_batched_tokens 与 chunk 大小。

19. 投机解码的加速比公式与关键变量？

结论：理想加速比 ≈ (1 + α·k) / (1 + c)，α 为接受率、k 为草稿长度、c 为草稿相对成本。
关键：α 随 k 增大而下降；草稿模型越强 α 越高但 c 越大。存在最优 k。
边界：大 batch 下 GPU 已饱和，投机收益下降；低 batch/低延迟场景收益最大。

20. FP8 的 e4m3 与 e5m2 分别用在哪？

e4m3：更高精度、更小动态范围，用于前向的权重/激活。
e5m2：更大动态范围、更低精度，用于梯度（梯度动态范围大）。
scaling：per-tensor 简单但受离群值影响；per-channel/per-block（如 MXFP8 的 32 元素块）更稳。训练常用 delayed scaling + amax 历史。
边界：FP8 的精度损失常表现为收敛变慢而非发散，必须看 loss 曲线与下游指标。

21. 为什么 torch.cuda.synchronize() 在性能代码里是 bug？

结论：它阻塞 CPU 直到所有 GPU 工作完成，破坏 CPU/GPU 异步流水，使 launch 与计算无法重叠；在计时场景还会把同步开销算进去。
正确做法：用 CUDA events 或 do_bench 计时；只在必须读结果时同步。
隐蔽来源：.item()、print(tensor)、if tensor:、动态 shape 触发的 cudaMemcpy。

22. CUDA graph 的捕获约束有哪些？

① 形状/地址固定（静态输入，或用 graph tree 管理多组）；② 捕获期间不能有 CPU 同步、不能动态分配（需用 graph 专用内存池）；③ 不能有依赖 CPU 值的控制流；④ 部分库调用/集合通信需要特定支持。
收益：消除每步几十到上百次 launch 的 CPU 开销，小 batch decode 收益最大。

23. Occupancy 越高越好吗？

结论：不一定。occupancy 用于掩盖延迟，但寄存器密集型 kernel（如 GEMM/FA）需要高寄存器复用，降低 occupancy 反而更快。
判断：看 ncu 的 achieved occupancy 与 stall reasons；若瓶颈是 long scoreboard（访存等待），才需要更高 occupancy。
边界：shared memory 用量也会限制 occupancy。

24. Shared memory bank conflict 是什么？怎么缓解？

结论：同一 warp 的多个线程访问同一 bank 的不同地址时会串行化。32 个 bank，按 4 字节粒度。
缓解：padding（如 [32][33]）、改变访问模式、使用 swizzle（CUTLASS 的 layout）、或改用 TMA。
检测：ncu 的 shared memory bank conflict 计数器。

25. TMA 相比 cp.async 的优势？

结论：TMA 是硬件多维拷贝引擎：不占寄存器、支持多维 tile 与自动边界处理、可与 mbarrier 异步同步，大幅降低地址计算与寄存器压力。
代价：需要 tensor map 描述符，灵活性低于手工 load；对小/不规则访问未必更优。
配套：通常与 warp specialization、多 stage 流水线一起用。

26. 什么是 MFU？给一个训练 step 算一遍。

结论：MFU = 6ND / (t × peak)，N 为参数量、D 为该 step 的 token 数、t 为 step 时间。
例：N=7e9、D=4e6，8×H100 bf16 峰值 8×990e12=7.92e15 FLOPS。理论耗时 = 6×7e9×4e6 / 7.92e15 ≈ 21.2s；若实测 50s，则 MFU ≈ 42%。
含义：MFU 低说明有通信、重算、数据或 bubble 损失；35–55% 属于良好。
边界：不同硬件的 peak 定义不同（是否含 sparsity），比较时必须统一。

27. Activation checkpointing 的显存/计算权衡？

结论：全量 checkpoint 把激活显存从 O(L) 降到 O(√L)（按层分组），代价是反向多一次前向，约 +33% 计算。
选择性：只对 attention/大激活重算，性价比最高。
边界：重算会改变数值（非确定性 op），需要时可开确定性模式。

28. 训练吞吐突然下降 20%，你的排查顺序？

① 确认基线（commit/驱动/数据分布）→ ② nsys 看是否有 launch gap 或通信等待 → ③ TORCH_LOGS 看 graph break/recompile → ④ ncu 抽查热点 kernel 是否退化 → ⑤ 检查 dataloader 与 CPU 利用率 → ⑥ 检查是否有隐式同步/动态 shape → ⑦ 检查 NCCL 拓扑与 bucket 配置 → ⑧ 检查显存压力是否触发 allocator 抖动。
原则：先分层排除，再深入；每步留证据。

29. NCCL hang 的排查顺序？

① TORCH_DISTRIBUTED_DEBUG=DETAIL 确认哪个 rank 未参与 → ② NCCL_DEBUG=INFO 看建链与算法选择 → ③ FlightRecorder / TORCH_NCCL_DUMP_ON_TIMEOUT 拿集合通信调用栈 → ④ py-spy dump 看 Python 侧是否卡在别处（如 dataloader）→ ⑤ 检查是否有 rank 因异常提前退出 → ⑥ 检查网络/IB 与 GPU 健康。
常见根因：某 rank 的 tensor shape 不一致、条件分支导致集合通信次数不同、未使用参数、异常被吞掉。

30. 确定性训练要开哪些开关？代价是什么？

开关：torch.use_deterministic_algorithms(True)、CUBLAS_WORKSPACE_CONFIG=:4096:8、NCCL_DETERMINISTIC=1、固定 seed、禁用非确定性 kernel（atomic 求和需改为确定性实现）。
代价：部分 kernel 变慢、NCCL 算法受限、可能无法使用某些高性能实现。
建议：调试期开启，生产训练通常关闭并依赖统计监控。

31. 在 PyTorch 里加一个新算子，需要改哪些地方？

① 在 native_functions.yaml 声明 schema 与 dispatch；② 写 C++/CUDA kernel（结构化 kernel 更好）；③ 加 meta/fake 实现（shape 传播）；④ 在 derivatives.yaml 或 torch.library 定义 autograd；⑤ 加 decomposition（给 Inductor）；⑥ 加 Inductor lowering（若不希望 fallback）；⑦ 写测试（correctness、gradcheck、device generic）；⑧ 更新文档与 BC 说明。
现代替代：torch.library.custom_op + register_fake + register_autograd，适合外部扩展。

32. AOTI 为什么能显著降低冷启动？

结论：它在编译期完成图捕获、lowering、kernel 编译与权重打包，运行时只加载 .so 与权重，不需要 Python、不需要 Dynamo、不需要 autotune 搜索。
对比：torch.compile 首次调用要跑完整编译链路（秒级到分钟级）。
边界：动态 shape/控制流支持有限；模型变更需重新编译；适合稳定线上模型。
